# awesome-vtt-core – project notes

Library module (`"library": true`) holding the code shared by `../awesome-vtt` (table mode) and `../awesome-vtt-mobile` (phone companion), by Stefano Pignataro. Foundry VTT v14, dnd5e 6.0.x (built against 6.0.5, verified with 6.0.6).

- **Why it exists:** these files used to be copied into both modules and kept in sync by hand. The user asked to move them into one library, required by both modules.
- **Socket:** `"socket": true`, channel `module.awesome-vtt-core`, used only by `prompts.mjs` to send `{ type: "promptDone", key }` so a prompt answered on one device closes on the player's others. The key is only checked for type and length; the worst a crafted message can do is close a prompt.
- **No scripts of its own:** the module has no `esmodules`. The other modules import its files by relative path (`../../awesome-vtt-core/scripts/…` from `scripts/`, one more `../` from subfolders).
- **Language prefix:** `AVTTC.`. Only labels the shared code itself produces go here; UI text belongs to each module.
- **Exhaustion:** changed through dnd5e's exhaustion effect itself (fixed id `dnd5eexhaustion0`, from `dnd5e.utils.staticID("dnd5eexhaustion")`): update its `system.level`, delete it at 0 (only if it still exists), or create it with `toggleStatusEffect("exhaustion", { levels })`. Don't set `system.attributes.exhaustion`: dnd5e then edits the effect afterwards, unawaited, from a possibly stale difference, which caused "already exists" / "does not exist" errors and changes that did nothing. Changes per actor are queued and wait for the effect to update.
- **Effect changes are queued and race-tolerant:** every effect change the modules make (conditions, exhaustion, toggleable effects, ending concentration) goes through `queueEffects` (one at a time per actor on this device), re-reads the effect just before changing it, and uses explicit states (`toggleStatusEffect(id, { active })`, `disabled: <value>`) so a repeat can't flip it back. `raceTolerant` treats Foundry's "already exists" / "does not exist" as done: the table screen, a phone and the GM can own the same character and change it at the same moment. Plain field updates (inspiration, currency, quantities, uses, slots) read the latest value and don't need this.
- **Conditions with levels:** dnd5e's `toggleStatusEffect("exhaustion")` only adds a level, so `toggleCondition` clears exhaustion when it's on and adds one level when it's off (through the exhaustion queue).
- **Uses and slots:** `changeUses` writes `system.uses.spent` (dnd5e stores uses spent); `changeSlots` writes `system.spells.<spellN|pact>.value`.
- **Keep the modules in sync (standing rule from the user):** every time something is added, removed or changed in the table or phone module, do the same in the other one through `awesome-vtt-core` (shared logic there; only templates, CSS, UI text and device-specific layout per module). If it's unclear whether or how a change applies to both, ask the user first.
- **What belongs here:** logic both modules need, not layout. Moved here on the user's request (2026-09-30) so the modules stay in sync with little overhead: the compact sheet's tabs, data, button actions and item descriptions, the quick actions, and chat filter / selection / sending (`sheet.mjs`), the automation prompts and their queue (`prompts.mjs`), the Dice panel and advantage choices (`dice.mjs`: `DicePanel`, `advModeChoices`), the Compendium and Journal panels (`panels.mjs`, one instance per seat / app, rendering through a callback with the module's own template), the section list and icons used by the phone's tab bar and the table's section bar, busy buttons, notices, chat sync and hook helpers (`ui.mjs`), and in `dnd5e.mjs` the HP modes, `needsTargets` (option `areasNeedTargets`: true on the phone, which has no map), `usageProblem` (returns a reason and data; each module words its own message) `summarizeDamage`, and the roll result notices (`onRollResult`, `summarizeRoll`, `rollNotice`; natural 20/1; pass/fail vs DC for check/save messages as dnd5e's `shouldDisplayChallenge` decides, with `shared: true` (the table, user's decision 2026-09-30) treating the screen as another player watching: `challengeVisibility` all/player show, none hides; hit/miss from `message.system.evaluatedTargets` (targets without AC left out) only when `attackRollVisibility` isn't none; DC/AC numbers never shown; an unreadable setting counts as hidden). Templates, CSS and UI text stay per module; when a feature exists in both modules, put its logic here and keep the same `data-action` names.
- **2026-10-04 (0.10.0):** `getSpells` / `togglePrepared` (Spells tab, `spellPrepare` sheet action; Actions now lists only spells with activities that can be cast now); `rollDamageAfterAttacks(applies)` (on `dnd5e.rollAttackV2`, before ammo is used up: `subject.rollDamage({ ability, attackMode, ammunition: Item, isCritical }, { configure: false })`, one tick later; the user wants attack + damage always rolled); `SECTION_ICONS.party`, `sharedInventory()`, `sectionList()` for the optional shared inventory module (its own folder, `../awesome-vtt-shared-inventory`). For that module, also here: `INVENTORY_TYPES` (exported), `moveCurrency(from, to, key, amount)` (giver updated first), `addNamedItem`, `copyItems` (dnd5e's `createWithContents`, stacking non-containers onto a same-name/type loose item), `moveItem` (whole stack, then `deleteContents`), `compendium.search(query, { types, filter })`, `runAction(..., action)` for buttons not named by `data-action`, and in `sheet.mjs` the `invToParty` action and the `toParty` context flag (both hosts' inventory button).
- **Tab orders (user's decision, 2026-10-04):** sheet tabs `SHEET_TABS` = actions, skills, spells, abilities, inventory, status (new tabs go after these). Quick actions have three tabs, `QUICK_TABS` (`quickTab()`, passed as `tab` / `tabLabel` to `quickActionsContext`): "quick" (only the character's actions: `actions` from `getActions`, both modules, each with an actions partial), "effects" (death saves, inspiration, quick conditions, HP field, concentration, exhaustion, toggleable effects), "rest" (short / long rest). Both modules use the `quickTab` data-action.
- **Favorites** (2026-10-04): `canFavorite`, `isFavorite`, `toggleFavorite` (dnd5e's `addFavorite` / `removeFavorite`, relative uuid via `foundry.utils.buildRelativeUuid`, as dnd5e's sheet star), `getFavoriteActions` (favorite items in dnd5e's order, max 8; no activity requirement: the user's Mace has `activities: {}`). Rows from `getActions`, `getSpells` and `getInventory` carry `favorite`; sheet and quick contexts carry `canFavorite`; sheet action `toggleFavorite`.
- **Game systems (user, 2026-10-04: add Shadow of the Demon Lord, see memory "sotdl-support"):** `system.mjs` default-exports a Proxy over the adapter of `game.system.id` (`dnd5e.mjs`, `demonlord.mjs`), plus `isSupported()`; modules use `import sys from …/system.mjs`. Both adapters export the same names (checked by a script: every `sys.X` used must exist in both). System-neutral helpers live in `common.mjs`. Adapter metadata: `FEATURES` (deathSaves, prompts, useSteps, party, itemRollMode, initiative "roll"|"speed"), `SHEET_TABS`, `ROLL_MODES` + `rollModeLabel` / `rollModeShort` (null → module label) + `rollModeScale` (SotDL {title, low, high} for the Next roll heading and the "Banes … Boons" ends, dnd5e null; 0.13.0, 2026-10-24, user found −3…+3 unclear) + `poolD20`, `FEATURES.abilityRollPrompt` (SotDL: sheet attribute rolls go through prompts.mjs `abilityRollPrompt`, a `local` prompt not broadcast with promptDone, when the module's client setting `askBoons` is on), `getRests()`, summary `stats` / `inspirationLabel`, quick `tracks` + `changeTrack`, `turnSpeed` / `setTurnSpeed`. SotDL specifics are documented at the top of `demonlord.mjs` (health = damage taken; boons/banes; no-dialog system methods with castings / uses / ammo / affliction checks done by us; uses stored as used-so-far strings; fast/slow turns). Phase 2 (0.12.0, 2026-10-04): `useItem(actor, itemId, mode, { targets, modifier })` (targets = token documents from the phone, else the user's map targets; the system's attack reads only `target.actor`), `itemNeedsTargets(item)` (weapons and attack spells; dnd5e stub false; talents/gear read map targets inside the system, so not asked), `rollDamageAfterAttacks` (a no-op in SotDL since 2026-10-10, user's request: damage is rolled with the card's button in both modules; it used to click the attack card's `.roll-damage` buttons), favorites in the actor flag `awesome-vtt-core.favorites` (item ids), `rollAbility(..., extra)` boons, coin/item moves (`moveCurrency`, `addNamedItem` as type "item", `copyItems` via `toObject` without `_id`, `wear` false, no containers, `moveItem`), and `getCurrency(actor)` in both adapters. `prompts.mjs` has per-system `BUILDERS`: SotDL "request" = the system's `.make-challengeroll` card (attribute name localized → key via `CONFIG.DL.attributes`, boons from `data-boonsbanes`, actor from the card's `data-token-id`), "initiative" = Fast / Slow choice (`setTurnSpeed`) in speed mode, else a roll; no death saves (the system has no fate roll; not automated). Smoke-tested in Node with mocks (DOM-dependent parts not), not in a live world.
- **Roll damage from the notice (user, 2026-10-10, all systems, both modules; only syntax-checked):** `summarizeRoll` returns `damage: true` for a roll whose damage can be rolled and that didn't miss (unknown hit = offered: no target / immune in SotDL, no AC target or hidden `attackRollVisibility` in dnd5e). `rollDamageFrom(message)`: dnd5e = the originating card's scaled activity `rollDamage({ ability, attackMode, ammunition: message.system.ammunitionItem, isCritical }, { configure: false })` as the card's Damage button; SotDL = `message.renderHTML()` (fires `renderChatMessageHTML`, where the system binds its buttons) and click every `.roll-damage`, with the resulting damage cards added up in one notice (`groupDamage`, 20 s, per actor, up to the button count). `FEATURES.autoDamage` (dnd5e true, SotDL false) + `system.mjs` `offersDamage(result, moduleAutoSetting)` hide the button when damage is already auto-rolled. `onRollResult` now also passes messages without dice to the adapter (Dice So Nice wait skipped): SotDL spells cast without an attack roll (and talents / items without a roll that have damage buttons) give `kind: "use"` (`rollNotice` → item name), found via the card's `.demonlord[data-item-id]` + token/actor. `ui.mjs` `fillNoticeAction(el, action)` draws the button and keeps its `run` (`takeNoticeAction(el)` in the module's click handler); `system.mjs` `damageAction(result, message, autoDamage, label, before?)` builds the action for both modules. Adapters export `CARD_TARGET_BUTTONS` (SotDL card buttons that read targets; dnd5e null); `demonlord.mjs` exports `targetOnSelect()`. `onRollResult` takes `enabled(message)`, checked before summarizing.
- **Changing an export:** both modules may use it. Search both before renaming or removing one, and bump the core's version together with the `requires` minimum in their `module.json` when needed.
- **Checks after edits:** `node --check`, JSON validation, and resolving every relative import from the two modules.
- **Foundry v14 source:** in `/Volumes/appdata/foundry-vtt/data/container_cache/`. **dnd5e source:** `../../systems/dnd5e/dnd5e.mjs`.
- **System differences outside the adapters (2026-10-04):** item descriptions are `system.description.value` in dnd5e but an HTML string `system.description` in SotDL (compendium preview handles both). `markSystem()` (system.mjs, called at init by both modules) sets `<body data-avtt-system="…">`; the modules' CSS gives chat messages a light card in non-dnd5e worlds, because only dnd5e restyles Foundry's messages for the dark theme (SotDL rolls were dark text on the dark panel; checked with a headless Chrome probe).

## Upstream watch

`.github/workflows/compat-review.yml` runs daily and has Claude review this module once for each new version of a dependency, following `.github/prompts/foundry-compat.md`.
- **Game systems:** a release of a system in `relationships.systems` newer than its `verified` version.
- **Foundry core:** a new Stable build, with a light review within the verified generation and a full review for a new generation.
- **Results:**
  - The module is fine: a pull request that bumps `verified`. It goes out with the next manual release.
  - A fix: a pull request.
  - Anything that needs the owner: an issue labelled `upstream-watch` and assigned to the owner.
  - New features worth using: an `enhancement` issue.
- **Access:** Claude works with read-only access (secret `CLAUDE_CODE_OAUTH_TOKEN`). A separate job opens the pull request and issues.
- **Isolation (tested 2026-10-11):**
  - **Before Claude runs:** the review job turns on the action's subprocess secret scrub and installs bubblewrap, so Claude's commands don't see the Claude token or any other process. It also blocks reading other processes' memory and removes sudo, and Docker is switched off (Docker access amounts to root).
  - **After Claude:** the steps that follow ignore variables and PATH entries its commands could plant, and make the diff in a fresh clone.
  - **Publishing:** the report job won't publish output that contains the token, or a piece of it, and deletes the review's artifact.
  - **What's left:** Claude's commands never see the token, so leaking it would take a way around the sandbox. The scan is a second line of defence.
- **Bookkeeping:** `.github/scripts/watch.sh` records what was reviewed on the `watch-state` branch. Run the workflow by hand with `force` to review again.
