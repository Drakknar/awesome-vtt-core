# awesome-vtt-core – project notes

Library module (`"library": true`) holding the code shared by `../awesome-vtt` (table mode) and `../awesome-vtt-mobile` (phone companion), by Stefano Pignataro. Foundry VTT v14, dnd5e 6.0.x (built against 6.0.5, verified with 6.0.6).

- **Why it exists:** these files used to be copied into both modules and kept in sync by hand. The user asked to move them into one library, required by both modules.
- **Socket:** `"socket": true`, channel `module.awesome-vtt-core`. `prompts.mjs` also relays SotDL challenge cards from the active GM (`challengeRelay`, GM senders only; see "Table notifications" below). `prompts.mjs` sends `{ type: "promptDone", key }` so a prompt answered on one device closes on the player's others (key checked for type and length only; the worst a crafted message can do is close a prompt; local prompts, e.g. the SotDL attribute roll, aren't sent). `vision.mjs` sends `visibleAsk` / `visibleTell`: the phone asks what its character can see; only a device that called `answerVisibility()` (the table screen) answers, after checking the sender owns the actor, with core's testVisibility logic limited to that actor's vision sources (vision lights, then each detection mode; blinded sources keep their special senses). The asker names the answerer (the table user from Awesome VTT's `tableUser` setting) and ignores other replies, asks nobody when that user is offline, waits 1.5 s, and covers at most `MAX_IDS` (1000) tokens. Module sockets reach every client, so others can read which tokens a character sees.
- **Settings (0.14.0):** the core has no init of its own, so `settings.mjs` `registerCoreSettings()` is called by both modules at init (first call registers, under the core's id): world `compendiumAdd` (on) gates the Compendium panel's **Add to inventory** (`CompendiumPanel` option `actor`, `compAddItem` → adapter `copyItems`, both systems, adapter `INVENTORY_TYPES`). `common.mjs` `onRollResult` option `others(message)` lets the table take rolls other users make (non-GM, seated actor); the table offers Roll damage only for its own rolls. Sheet tab `bio` in both systems (`getBio`: SotDL ancestry/paths/professions/languages/religion/appearance/description, dnd5e species/background/classes/alignment/faith/personality/appearance/biography; `sheet.enrichSheet` enriches the description, modules await it before rendering). Sheet rolls can ask first (`FEATURES.abilityRollPrompt`, `prompts.mjs` `askSheetRoll` with a per-system `BUILDERS.sheetRoll`: SotDL attributes for boons/banes, dnd5e checks/saves/skills for advantage; the modules' client setting `askBoons`, on in SotDL, off in dnd5e).
- **No scripts of its own:** the module has no `esmodules`. The other modules import its files by relative path (`../../awesome-vtt-core/scripts/…` from `scripts/`, one more `../` from subfolders).
- **Language prefix:** `AVTTC.`. Only labels the shared code itself produces go here; UI text belongs to each module.
- **Exhaustion:** changed through dnd5e's exhaustion effect itself (fixed id `dnd5eexhaustion0`, from `dnd5e.utils.staticID("dnd5eexhaustion")`): update its `system.level`, delete it at 0 (only if it still exists), or create it with `toggleStatusEffect("exhaustion", { levels })`. Don't set `system.attributes.exhaustion`: dnd5e then edits the effect afterwards, unawaited, from a possibly stale difference, which caused "already exists" / "does not exist" errors and changes that did nothing. Changes per actor are queued and wait for the effect to update.
- **Effect changes are queued and race-tolerant:** every effect change the modules make (conditions, exhaustion, toggleable effects, ending concentration) goes through `queueEffects` (one at a time per actor on this device), re-reads the effect just before changing it, and uses explicit states (`toggleStatusEffect(id, { active })`, `disabled: <value>`) so a repeat can't flip it back. `raceTolerant` treats Foundry's "already exists" / "does not exist" as done: the table screen, a phone and the GM can own the same character and change it at the same moment. Plain field updates (inspiration, currency, quantities, uses, slots) read the latest value and don't need this.
- **Static status ids (0.15.1 / 0.16.0, 2026-10-25, temporary):** Foundry v14's `fromStatusEffect` throws "Status effects with implicit statuses must have a static _id" for a status that brings others with it and has no `_id`. With an `_id`, core's `toggleStatusEffect` and the token HUD only find the effect with that `_id`. SotDL 6.1.11/6.1.12 registers Blinded and Unconscious (both add core's "blind") without one, at its own setup hook, and creates such effects itself with random ids (`findAddEffect`: Dying or Asleep → Unconscious; the sheet's affliction toggle; the afflictions compendium). `system.mjs` `fixStatusIds()` (exported, called at init by `markSystem()` and by `awesome-vtt-shared-inventory`; hooks added once) gives such statuses `avtt<id>` padded to 16 characters (`avttunconscious0`, `avttblinded00000`) at setup, and a `preCreateActiveEffect` hook gives that `_id` (with `keepId`) to effects created on an actor with one of those statuses, unless the actor already has it. `demonlord.mjs` `toggleCondition` turns a status off by deleting every effect of the actor that has it (effects from before 0.16.0 keep random ids), and on with `toggleStatusEffect`. Reviewed 2026-10-25 by reading core 14.369 and demonlord 6.1.12; not yet run in a live world. Keep it until the system sets its own `_id`s and `minimum` can be raised; the upstream watch checks this on every demonlord and core review.
- **SotDL 6.1.13 / 6.1.14 (0.17.0, 2026-11-06, issues #14 and #22; only syntax-checked):**
  - **Transformed characters** (dnd5e polymorph / wild shape too): the system creates a new actor flagged `flags.<system>.isTransformed` (dnd5e `isPolymorphed`) + `originalActor`, relinks the tokens and deletes it on `revertOriginalForm`. `common.mjs` `transformHelpers(flag)`, exported by both adapters: `isTransformed`, `originalId` (the character a form came from; seats and the phone keep that id), `currentForm` (the newest form of a character this user owns, else the character), `revertForm`, `isForm` (a form, or one a player's revert left behind: the system then removes only `<flag>` and keeps `originalActor`, pointing at another actor; character lists and seat choices leave both out; never an actor whose `originalActor` is itself, nothing on systems without these flags), `transformChanged(actor, change, ids?)` (for `updateActor`: only changes to the transform flags `<flag>` / `originalActor`, set or `-=` removed, on one of `ids` or a form of one; both modules' re-renders use it, since the system writes other flags often, e.g. SotDL afflictions on NPCs). Quick actions show **Revert** (`revert` in `quickActionsContext`, sheet action `revertForm`) only with the map (`canvas?.ready`), so in practice on the table only: both systems relink the tokens to the original only `if (canvas.ready)` (demonlord `revertOriginalForm`, dnd5e too), so a revert from a canvas-less client (the phone's No-Canvas mode) would leave them on a deleted (GM) or orphaned (player) form. Still waiting (upstream watch): `fixStatusIds`, since 6.1.13 still gives Blinded / Unconscious no static `_id`.
  - **Boon and bane sources** (6.1.14): the system's roll dialog lists them and the roll methods take a trailing `selection = { disabled: [ids] }`. `demonlord.mjs` has a copy of the system's unexported `collectBoonSources` (`src/module/rolls/boon-sources.js`; keep in step on system updates) and `boonSources(actor, { attribute | itemId, targets })` (null before 6.1.14 or for an item without an attack roll; the system's hidden target sources labelled "Other" for players; dnd5e: always null). `rollAbility(..., extra, disabled)` and `useItem(..., { disabled })` pass the selection; older systems ignore the argument, so no `minimum` change. Prompts get `sources()` (read on every render) and `disabled`; `PromptQueue#toggleSource(id)`, `context().sources` (exported `sourceRows(sources, disabled)`: `{id, label, value: "+1"/"−1", enabled}`; the phone's use dialog also uses it and `toggleSourceIn`), `choose` passes the ids to `run(mode, disabled)`. The challenge request and sheet attribute prompts list sources; `askItemRoll(queue, actor, itemId)` (new local prompt `itemRollPrompt`) asks before an item attack that has sources. Modules: button `data-action="promptSource" data-source-id`.
  - **Temporary effects switched on again** restart their duration: `demonlord.mjs` `toggleEffect` passes `common.mjs` `toggleEffect`'s `extra(effect, disabled)` fields, only when switching on: Foundry 14's stored `start` (`ActiveEffect.getEffectStart()`, read in the 14.370 client source; else `{ time, combat, round, turn }` from `game.time` / `game.combat`). Deliberately unlike demonlord 6.1.14's own sheet toggle, which sends `duration._worldTime`: a derived field (`_prepareDuration` sets it), not stored data. Owner's decision, 2026-11-06; not run in a live world.
- **Table notifications (0.18.0, 2026-11-06, owner-approved scope; only lint-checked, not run in a live world):**
  - **Challenge relay:** demonlord 6.1.14's GM "request challenge roll" button whispers each `makechallengeroll` card to `ChatMessage.getWhisperRecipients(actor.name)` (users whose assigned character has that name), so the table user (no character, on purpose) doesn't get it. `prompts.mjs` `relayChallenges(recipients)` (called on every client at ready by Awesome VTT; acts only on `game.users.activeGM`, only for whispered cards authored by a GM (`message.author?.isGM`), only to the active users `recipients(actor)` returns for the card's character and that aren't among the whisper; the table returns its user only for a seated character, see its notes) sends `{ type: "challengeRelay", to: [userId], messageId, actorUuid, attribute, boons, userId }` on the core channel. `initPrompts({ relayed: true })` registers its socket handler as `(...args)` and accepts a relay only when `args.length === 2`, `game.users.get(args[1])?.isGM` and `to` contains this user, after `validRelay` (16-char ids, uuid `Actor.<id>` or `Scene.<id>.Token.<id>` only (`CHALLENGE_UUID`; `challengeActor` also rejects a resolved document with a `pack`, on the card path too), attribute a `CONFIG.DL.attributes` key, integer boons |n| ≤ 20). The card path and the relay share `readChallengeCard` / `challengePrompt` and the key `challenge:<messageId>:<actor uuid>`; a per-device set prompts each card once. Option `announce(prompt, prompted)` reports every challenge request for one of the device's characters (the table tells the other seats). No-op in dnd5e (no `readChallenge` builder). **Unverified sender layout:** that a module socket handler gets `(data, senderUserId)` (the id added by the server) has not been checked in a live world. A relay arriving with another number of arguments is ignored and logged once (`console.warn`, "awesome-vtt-core | challengeRelay ignored: the socket handler got N arguments"). To check live: with the table client and a GM connected, have the GM request a challenge roll from a seated character and look at the table client's console; a prompt in the seat and no warning means the layout is right (or set a breakpoint in the handler and inspect `args`). Needs a connected GM. Module sockets reach every client, so others can read who was asked for what (the card's speaker says as much).
  - **SotDL useItem hooks:** when no targets are passed, `useItem` calls `Hooks.call("awesome-vtt-core.preUseItem", actor, item)` before reading the user's targets (a listener returning false cancels the use before anything is spent; `useItem` then returns false) and `Hooks.callAll("awesome-vtt-core.useItem", actor, item, used)` afterwards (in `finally`). `used` is true only when the use went ahead: `attackWith` / `castSpell` / `useTalent` / `useGear` return `true`, or `false` when they stop first (no ammunition, castings or uses left, an affliction; the `stopped(message)` helper warns and returns false, since `ui.notifications.warn` returns an object). `useItem` returns `used`. dnd5e exports a `targetOnSelect()` stub (false) so the table can ask either adapter. The table's target rule uses them.
  - **`healthState(actor)`** in both adapters: `{ damage, statuses }`, damage a rising number (SotDL damage taken; dnd5e −HP, temp HP left out since rests clear it), statuses SotDL `injured` / `incapacitated` / `dead`, dnd5e `unconscious` / the defeated status. `common.mjs` `statusLabel(id)`. `ui.mjs` notice kinds `request` (bell) and `hurt` (heart-crack).
  - **Known upstream limitation, not handled:** item macros (a system bug; the table doesn't try to work around it).
- **Conditions with levels:** dnd5e's `toggleStatusEffect("exhaustion")` only adds a level, so `toggleCondition` clears exhaustion when it's on and adds one level when it's off (through the exhaustion queue).
- **Uses and slots:** `changeUses` writes `system.uses.spent` (dnd5e stores uses spent); `changeSlots` writes `system.spells.<spellN|pact>.value`.
- **Keep the modules in sync (standing rule from the user):** every time something is added, removed or changed in the table or phone module, do the same in the other one through `awesome-vtt-core` (shared logic there; only templates, CSS, UI text and device-specific layout per module). If it's unclear whether or how a change applies to both, ask the user first.
- **What belongs here:** logic both modules need, not layout. Moved here on the user's request (2026-09-30) so the modules stay in sync with little overhead: the compact sheet's tabs, data, button actions and item descriptions, the quick actions, and chat filter / selection / sending (`sheet.mjs`), the automation prompts and their queue (`prompts.mjs`), the Dice panel and advantage choices (`dice.mjs`: `DicePanel`, `advModeChoices`), the Compendium and Journal panels (`panels.mjs`, one instance per seat / app, rendering through a callback with the module's own template), the section list and icons used by the phone's tab bar and the table's section bar, busy buttons, notices, chat sync and hook helpers (`ui.mjs`), and in `dnd5e.mjs` the HP modes, `needsTargets` (option `areasNeedTargets`: true on the phone, which has no map), `usageProblem` (returns a reason and data; each module words its own message) `summarizeDamage`, and the roll result notices (`onRollResult`, `summarizeRoll`, `rollNotice`; natural 20/1; pass/fail vs DC for check/save messages as dnd5e's `shouldDisplayChallenge` decides, with `shared: true` (the table, user's decision 2026-09-30) treating the screen as another player watching: `challengeVisibility` all/player show, none hides; hit/miss from `message.system.evaluatedTargets` (targets without AC left out) only when `attackRollVisibility` isn't none; DC/AC numbers never shown; an unreadable setting counts as hidden). Templates, CSS and UI text stay per module; when a feature exists in both modules, put its logic here and keep the same `data-action` names.

## Upstream watch

`.github/workflows/compat-review.yml` runs daily and has Claude review this module once for each new version of a dependency, following `.github/prompts/foundry-compat.md`.
- **Game systems:** a release of a system in `relationships.systems` newer than its `verified` version.
- **Foundry core:** a new Stable build, with a light review within the verified generation and a full review for a new generation.
- **Results:**
  - The module is fine: a pull request that bumps `verified`. It goes out with the next manual release.
  - A fix: a pull request.
  - Anything that needs the owner: an issue labelled `upstream-watch` and assigned to the owner.
  - New features worth using: an `enhancement` issue.
- **Access:** Claude works with read-only access (secret `CLAUDE_CODE_OAUTH_TOKEN`). A separate job opens the pull request and issues.
- **Isolation (tested 2026-10-11):**
  - **Before Claude runs:** the review job turns on the action's subprocess secret scrub and installs bubblewrap, so Claude's commands don't see the Claude token or any other process. It also blocks reading other processes' memory and removes sudo, and Docker is switched off (Docker access amounts to root).
  - **After Claude:** the steps that follow ignore variables and PATH entries its commands could plant, and make the diff in a fresh clone.
  - **Publishing:** the report job won't publish output that contains the token, or a piece of it, and deletes the review's artifact.
  - **What's left:** Claude's commands never see the token, so leaking it would take a way around the sandbox. The scan is a second line of defence.
- **Bookkeeping:** `.github/scripts/watch.sh` records what was reviewed on the `watch-state` branch. Run the workflow by hand with `force` to review again.
